# 실제 이용자 커뮤니티

`/community`는 SQL v2의 `posts`, `comments`, `my_content_ids()`를 그대로 사용한다. DB 구조/RLS 변경이나 SQL 실행 없이 클라이언트만 연결했다. 기존 하차 공유 소스는 이번 작업에서 수정하지 않았다.

## 저장과 권한

- 공개 조회는 세션 없는 public client를 사용한다. 읽기만으로 익명 사용자를 생성하지 않는다.
- 새 글·댓글을 등록할 때 기존 `ensureAnonymousAuthor()`로 익명 세션을 준비하거나 재사용한다. 별도 로그인 화면은 없다.
- 수정·삭제는 기존 작성자 클라이언트로 요청한다. 이 동작에서 새 익명 계정을 자동 발급하지 않는다. 관리 버튼은 `my_content_ids()`의 종류별 본인 ID만 사용하며 서버 RLS가 최종 권한을 검증한다.
- 모든 SELECT는 허용 컬럼을 열거한다. `owner_id`, 토큰, 이메일, 개인별 고정 닉네임은 표시하지 않는다. '익명 이용자'는 작성자 신원을 뜻하지 않는 공통 안내 이름이다.
- posts INSERT/UPDATE는 line_id, line_station_id, category, title, body만 보낸다. comments INSERT는 post_id/body, UPDATE는 body만 보낸다. 작성자·ID·시각은 DB가 결정한다.
- 수정·삭제에는 id 및 읽었던 updated_at 필터를 함께 보내 다른 창의 최신 수정을 덮어쓰지 않는다. 0행이면 성공 안내 대신 새로고침을 안내한다.
- 삭제는 확인 대화상자를 거친다. 게시글 삭제 시 기존 외래키의 ON DELETE CASCADE로 다른 사용자의 댓글도 함께 삭제된다. 이 동작을 확인 문구로 알린다.
- 성공 응답 후 목록/상세/본인 ID를 다시 조회한다. 실패 시 입력값을 유지하고 원인별 오류를 안내한다. 저장 결과가 불확실한 통신 오류는 재등록 전에 새로고침으로 확인한다. 쓰기·삭제 자동 재시도는 SDK 수준에서도 차단한다.

## 표시·검색

- 기존 빨간색 그라데이션, 카드, 분류 버튼, 작성 폼, 상세/댓글 화면 구성을 유지한다.
- MOCK_POSTS, 직원 모드, 가짜 기관 답변/처리 상태/조회 수를 제거했다. 공식 철도기관 민원 접수가 아님을 표시한다.
- 빈 데이터와 조회 실패는 다른 화면으로 표시한다. 가짜 데이터를 대신 넣지 않는다.
- 등록/검색용 노선·역은 DB에서 검증한 신분당선 16개 역을 사용한다. 역 저장 값은 stations.id가 아니라 line_stations.id다. 게시글은 노선 필수, 역 선택 사항이다.
- 제목·본문은 React 텍스트로 출력하며 HTML을 실행하지 않는다. 제목 100자, 본문 5,000자, 댓글 2,000자 제한과 공백 검증을 한다.
- 분류/노선/역 필터는 DB 조회 조건으로 적용한다. 목록과 댓글은 각각 20개 단위로 페이지를 나눠 Supabase 기본 응답 한도로 누락되지 않게 한다. 새 댓글이 마지막 페이지에 있으면 '다음 댓글'로 이동한다.
- 새로고침 버튼으로 다른 사용자의 변경을 확인한다. Realtime 구독이나 자동 푸시는 이번에 추가하지 않았다.

## 작성 제한·봇 방지

기존 DB 트리거는 게시글 작성+수정을 분당 2회/하루 20회, 댓글 작성+수정을 분당 5회/하루 100회로 제한한다. 빠르게 테스트하면 정상적인 수정도 차단될 수 있으므로 1분 정도 기다린 뒤 재시도한다. 하루 기준은 기존 SQL의 UTC다. 삭제는 이 횟수에 포함되지 않는다.

기존 Turnstile 컴포넌트와 공개 site key를 사용하며, 새 익명 가입 시 받은 CAPTCHA 토큰을 Auth에 전달한다. 보호를 실제로 강제하려면 Supabase Auth의 CAPTCHA 설정과 localhost/Preview 호스트 허용 설정이 함께 맞아야 한다. Secret 키는 Auth 대시보드에만 둔다. 기존 익명 ID를 반복 발급하면 사용자별 제한을 우회할 수 있으므로 공개 전 Auth CAPTCHA·인증 요청 제한도 확인해야 한다. 이 작업은 대시보드 설정을 변경하지 않는다.

## 브라우저에서 확인하기

1. 일반 브라우저 A에서 `http://localhost:3000/community`를 연다. 비어 있으면 '아직 작성된 게시글이 없습니다.'가 보여야 한다.
2. '게시글 작성하기'를 누르고 분류, 신분당선, 역(선택), 제목, 내용을 입력해 등록한다. 새로고침 후 DB에서 읽은 동일한 글이 보이는지 확인한다.
3. 상세에서 A의 '내 글'과 수정·삭제 버튼을 확인한다. 한 번 수정하고 새로고침해 유지되는지 확인한다.
4. 별도 시크릿 창 B에서 같은 주소를 열고 A의 글을 조회한다. A의 글에 B가 사용할 수정·삭제 버튼은 없어야 한다.
5. B에서 댓글을 등록한다. A에서 상세의 '새로고침'을 눌러 댓글이 보이고 B의 댓글에 수정·삭제 버튼이 없는지 확인한다.
6. B에서 본인 댓글을 수정하고 새로고침한다. A에서도 새로고침해 변경을 확인한다. B에서 본인 댓글을 삭제한다.
7. 필요하면 A에서도 댓글을 등록하여 B가 A의 댓글을 관리할 수 없는지 반대로 확인한다.
8. A에서 게시글을 삭제한다. 댓글이 함께 삭제된다는 확인 창이 나와야 한다. B에서 상세를 새로고침하면 삭제 안내가 나와야 한다.
9. 노선·역·분류별 필터와 결과 없는 조건을 확인한다. 네트워크를 끊고 새로고침하면 빈 목록 문구 대신 오류가 표시되어야 한다.
10. 두 탭에서 같은 글 수정을 열어 한 쪽을 먼저 저장한 뒤 나머지 쪽에서 저장한다. 이전 버전 저장은 거절되고 새로고침 안내가 나와야 한다. 먼저 저장한 내용을 보존해야 한다.

브라우저 데이터는 지우지 않는다. 같은 일반 브라우저 탭 둘은 동일한 작성자일 수 있으므로 A/B 권한 시험은 일반 창과 시크릿 창 또는 서로 다른 브라우저를 사용한다.

## 검사 명령

- `npm test`: 격리된 HTTP 응답 기반 테스트와 기존 하차 공유·인증 테스트. 실제 DB에 시험 글을 넣지 않는다.
- `npm run typecheck`: 타입 검사.
- `npm run build`: 기존 output: export 정적 빌드.
- `node node_modules/tsx/dist/cli.mjs scripts/check-community.ts`: 실제 DB의 공개 조회만 확인. 키·제보 내용·작성자 ID를 출력하지 않는다.

실제 두 사용자 CRUD 성공 여부는 위 브라우저 시험으로 확인한다. 모의 HTTP 테스트 통과를 실제 DB 쓰기 성공으로 간주하지 않는다.

참고한 공식 문서: [Next.js 15 정적 내보내기](https://nextjs.org/docs/15/app/guides/static-exports), [Supabase 컬럼별 권한](https://supabase.com/docs/guides/database/postgres/column-level-security). 구현 권한 목록은 저장된 SQL v2와 직접 대조했다.
